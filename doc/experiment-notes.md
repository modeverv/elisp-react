# 実験メモ

問い：最初期の React（2013年ごろ。`createClass`、props、state、`render`、差分計算）と同等のことが Emacs Lisp でできるか。

## 第1段階の結果（2026-11-14）

できました。カウンターと、親が state を持つカウンター一覧の2つのページが、実際のブラウザで動いています。

- React にあたる部分はすべて Emacs Lisp です（`lisp/react.el`、450行）。要素、コンポーネント、props、state、差分計算、`did-mount` / `will-unmount` が入っています。
- JavaScript は210行で、コンポーネントという概念を知りません。番号から DOM ノードへの対応表と、11種類の DOM 操作を適用する処理だけです。
- クリック1回あたり約1.2ミリ秒で画面に反映されます（200連打で244ミリ秒）。体感の遅れはありません。
- 再描画しても DOM ノードは作り直されません。テストで確認しています。

## Lisp で書いてよかった点

- **要素がそのままデータ**：`(div (:class "x") "text")` は引用したリストで、JSX もビルド時の変換も要りません。動的な部分はバッククォートで埋めます。
- **条件分岐や繰り返しが普通の Lisp**：`,(if ...)` や `,@(mapcar ...)` で済み、JSX 特有の書き方がありません。
- **ハンドラがクロージャ**：`(lambda (_event) (react-set-state self ...))` がインスタンスをそのまま捕まえます。`this` の束縛問題がありません。
- **ブラウザなしでテストできる**：DOM 操作がデータなので、「要素をマウントしてイベントを送り、操作列を比べる」テストがネイティブの Emacs で数ミリ秒で走ります。
- **差分計算が短い**：`pcase` と構造体で、差分計算の中心部分は100行ほどです。

## 書きにくかった点

- **バッククォートの中のカンマ**：ハンドラや計算値のたびに `,` が要ります。忘れると「関数ではなくリストがハンドラになる」という分かりにくい失敗になります。マクロを入れる動機になる箇所です。
- **不変データがない**：`react-set-state` は新しい plist を設定しますが、入れ子のリストを更新するコードは手で「新しいリストを作る」ように書く必要があります（`examples/counters/counters.el` の `add` と `remove`）。うっかり破壊的に変更しても、言語は止めてくれません。
- **plist の更新が冗長**：1項目だけ変えたレコードを作るのに、全項目を書き直しています。小さな補助関数が欲しくなります。
- **タグ名とコンポーネント名が同じ名前空間**：`(counter ...)` がコンポーネントか HTML タグかは、定義の有無で決まります。名前空間がないので、大きくなると衝突の心配があります。
- **真偽値の扱い**：Lisp の `nil` は「偽」「空」「なし」を兼ねます。JSON の `false` と `null` を区別したい場面では `:false` を使う規約が要ります。
- **lexical-binding が必須**：クロージャに頼るので、動的束縛で評価されると壊れます。評価サービス側で常に lexical にしています。

## 第2段階の結果（2026-11-14）

key つきの差分、TODO アプリ、`jsx` マクロを追加しました。

### key つきの差分

- 子は「key があれば key、なければ key なしの子の中での順番」で対応づけます。key のないリストは、これまでどおり位置で対応します。
- 並べ替えでは、元の順序を保っている子の最長の組（最長増加部分列）を動かさず、それ以外だけを動かします。4行のうち最後の行を先頭に移す操作は、DOM 操作1回です。最初期の React の方式だと3回になります。
- 差分計算全体を、DOM の模型に対する乱数テストで確かめています。削除、追加、シャッフルを300回繰り返し、模型とマウント済みの木が一致することと、state が key に付いて移動することを確認します。ネイティブの Emacs で0.2秒です。
- 実装は部分列の計算を含めて約80行です。Lisp のハッシュ表とベクタで素直に書けました。

### TODO アプリ（`examples/todo/`）

- 追加、完了の切り替え、削除、並べ替え、名前の編集、フィルタ、完了済みの一括削除ができます。
- 各行は自分の state（編集中かどうかと、入力途中の文字列）を持ちます。ある行を編集している最中に、他の行を動かしたり消したりしても、編集中の行は DOM ノードも入力途中の文字列も保ちます。ブラウザのテストで確認しています。
- データの更新は「todo のリストを受け取って新しいリストを返す純粋な関数」に分けました（`todo-change`、`todo-move-before`、`todo-visible`）。こうすると、ブラウザなしでテストでき、破壊的変更をしていないことも確かめられます。

### `jsx` マクロの書き味

- **カンマがなくなり、読みやすくなりました。** `(p (format "Count: %d" count))` のように、マークアップの中にそのまま Lisp を書けます。ハンドラの `,(lambda ...)` のカンマ忘れという失敗もなくなります。
- **規則は JSX と同じにしました。** HTML タグか、大文字で始まる名前（コンポーネント）で始まるリストがマークアップで、それ以外は Lisp です。マクロ展開の時点では「その名前のコンポーネントが定義済みか」を調べられない（後で定義されるかもしれない）ので、名前の形で決める必要がありました。
- **Lisp の中に入ったら `jsx` を書き直す必要があります。** `(when cond (jsx (strong "x")))` や `(mapcar (lambda (x) (jsx (li x))) xs)` のように書きます。JSX では `{}` の中にそのままタグを書けるので、ここは JSX より一手間多い点です。
- **素のリストはそのまま土台として残っています。** `jsx` は `list` の呼び出しに展開されるだけで、できあがるものは同じデータです。

### 新しく分かった書きにくさ

- **描画中の「前の行」の受け渡し**：TODO の「↑」ボタンは「1つ前に見えている行」を知る必要があり、`mapcar` の中で変数を書き換えて渡しています。関数型できれいに書くには、インデックスつきの写像か、隣接ペアを作る補助が欲しくなります。
- **アクションの分岐**：行から親への依頼を `(funcall act 'toggle id)` のようにシンボルで分岐させました。Redux の reducer に近い形で、Lisp の `pcase` とは相性がよいです。
- **イベントハンドラの中で古い値を捕まえる危険**：`render` の時点の `todos` をクロージャが捕まえると、連続したイベントで古い state を元に更新してしまいます。ハンドラの中では `(react-state self :todos)` を読み直す規約にしました。React の「setState に関数を渡す」と同じ問題です。

## 第3段階の結果（2026-11-14）

ページへの依頼（フォーカス、`localStorage`）と、非同期（タイマー、`fetch`）を追加しました。

### 仕組み

- Lisp はページに応答している間しか動かないので、待つことができません。そこで「ページにやってほしいこと」も、DOM 操作と同じ列にデータとして載せて返すことにしました。ページ側がブラウザの非同期 API で実行し、結果が出たら Lisp を呼び直して、待っていた関数を実行します。
- wasmacs の評価サービスには手を入れていません。すべて `react.el` と土台の JavaScript の中で済みました。
- 新しい機能を足すのは、土台にコマンドを1つ、Lisp に薄い関数を1つ書くだけです。`react-set-timeout`、`react-set-interval`、`react-fetch` はどれも数行です。

### できるようになったこと

- **フォーカス**：TODO の編集を始めると、入力欄にフォーカスが移り、文字列が選択されます。要素に `:ref` で名前を付け、`:did-update` の中で `react-focus` を呼びます。
- **保存**：TODO のリストが `localStorage` に保存され、リロードしても残ります。Lisp のデータ（plist のリスト）をそのまま印字して保存します。読み出しは同期です（起動時に土台がページの保存内容を Lisp に渡しておきます）。
- **タイマーと fetch**：`examples/async/` に、時計（インターバル）、リマインダー（タイムアウト）、データ読み込み（読み込み中・成功・失敗の表示）があります。時計はコンポーネントが外れるとインターバルを止めます。

### 観察

- **制約がそのまま良い設計になりました。** 「Lisp は副作用を自分で実行できず、データとして返すしかない」という制約は、Elm や Redux のミドルウェアが意図的に採用している設計と同じ形です。副作用がデータなので、タイマーも fetch もブラウザなしでテストできます（依頼の中身を比べ、応答を手で渡す）。
- **全体の構造は React Native の初期のブリッジに近いです。** あちらは JavaScript のスレッドが UI 操作を直列化してネイティブ側に送り、イベントを受け取ります。ここでは Emacs がその JavaScript の役で、ブラウザの DOM がネイティブの役です。
- **コールバックで十分でした。** 2013年の React も `componentDidMount` の中でコールバック式の通信をしていたので、当時と同じ書き方になります。`async`/`await` 相当は、Emacs の `generator.el` の上に作れる可能性がありますが、試していません。
- **`did-update` に前回の state を渡す設計が要になりました。** 「編集が始まった瞬間」や「リストが変わった瞬間」を、前回との比較で判定できます。state を差し替え方式にしてあるので、`eq` で変化を検出できます。

## 速度と起動時間（2026-11-14）

大きなリストで計測したところ、最初の実装は実用にならない遅さでした。原因と対策は次のとおりです。

- **原因**：ページから送った Lisp は、Emacs のインタープリタで実行されていました。インタープリタは、呼び出しのたびにマクロ（`jsx`）を展開し直し、差分計算の `pcase` や構造体アクセスもコンパイルなしで実行します。
- **対策**：土台が各ファイルを Emacs の中でバイトコンパイルしてから読み込むようにしました。コンパイル結果は `localStorage` に保存し、ソースが変わるまで再利用します（`react.el` のコンパイルは約0.3秒かかるため）。

ページ内の Emacs（WebAssembly）での計測です。

| 操作 | 評価のみ | バイトコンパイル |
|---|---|---|
| 1000行のマウント | 1724 ms | 67 ms |
| 1000行、変化なしの再描画 | 4676 ms | 134 ms |
| 1000行のうち1行だけ変更 | 4688 ms | 134 ms |
| 1000行を逆順に | 4728 ms | 136 ms |
| カウンターのクリック1回（往復こみ） | 1.2 ms | 0.14 ms |

- 「1行だけ変更」が「変化なし」と同じ時間なのは、親が再描画されると全行の `render` をやり直すためです（`should-update` 相当がありません）。DOM 操作は1件だけ出ています。
- 起動時間は、wasmacs の評価サービスが Emacs 本体をブラウザの Cache Storage に保存するようになり、公開サイトで初回約2.6秒、2回目以降は約0.2秒になりました。

## まだやっていないこと

- **`should-update` 相当**：親が再描画されると、子も必ず再描画されます。
- **イベントの詳細**：ハンドラに渡るのは `:type :value :checked :key` だけです。`preventDefault` は submit だけ土台が自動で行います。
- **SVG、context**：未対応です。
- **エラー処理**：ハンドラ内のエラーはページ下部に赤い帯で表示されるだけです。
- **初回のダウンロードサイズ**：Emacs 一式で約150MBあります。2回目以降はブラウザのキャッシュから起動します。

## 次の段階の候補

1. `should-update` 相当（props が変わらない子の再描画を省く）。1000行で134ミリ秒かかっている部分です。
2. `async`/`await` 風の書き方（`generator.el`）を試して、コールバックと書き味を比べる。
3. イベント情報の拡充（座標、修飾キー）と、`preventDefault` を Lisp 側から指定する方法。
